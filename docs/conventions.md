# Conventions

Detailed conventions — referenced from `CLAUDE.md` with `@docs/conventions.md` when needed.

## API shape

- All endpoints under `/api/`. The SPA is served from `/` for everything else (with a SPA fallback for client-side routes).
- Request and response bodies are JSON.
- Validation: every handler parses its input through a Zod schema from `packages/shared`. The same schema is used by the client form.
- Success responses: `{ data: ... }`. Error responses: `{ error: { code: string, message: string, details?: unknown } }`. HTTP status codes are still set correctly.
- Mutating endpoints that affect dashboard state must broadcast an SSE event after committing.

### SSE events

- Endpoint: `GET /api/events`. Each connected client receives a stream.
- Event shape: `{ type: string, payload: unknown }` serialized as the SSE `data:` field.
- Event types:
  - `instance-updated` — a task instance was created/updated. Payload: `{ taskId, date, status }`.
  - `task-changed` — a task template was created/updated/deleted. Payload: `{ taskId }`.
  - `member-changed` — family member added/edited/removed/reordered.
  - `calendar-synced` — calendar cache was refreshed. Payload: `{ syncedAt }`.
  - `day-rolled-over` — daily rollover completed. Payload: `{ date }`.
  - `settings-changed` — settings updated.
- Clients use TanStack Query and invalidate the appropriate query keys when an event arrives. The browser's `EventSource` reconnects automatically.

## Database

- One SQLite file. Path configurable via env (`DB_PATH`); default `./data/app.db` in dev, `/var/lib/family-planner/app.db` in production.
- `journal_mode = WAL` always. Set on connection open.
- `synchronous = NORMAL` is fine for this workload.
- `foreign_keys = ON` always.
- Migrations live in `apps/server/drizzle/`. Generated by `drizzle-kit`; applied at server startup.

## Recurrence rules

Stored on `tasks.recurrence_kind` and `tasks.recurrence_config` (JSON). Four kinds:

- `none` — one-off, active only on `start_date`.
- `weekdays` — `{ days: ("mon"|"tue"|"wed"|"thu"|"fri"|"sat"|"sun")[] }`.
- `every_n_days` — `{ n: number }`. Day `D` occurs iff `(D - start_date)` is a multiple of `n`.
- `monthly` — either `{ kind: "day_of_month", day: 1..31 }` or `{ kind: "nth_weekday", n: 1..5, weekday: "mon"|... }` (e.g. first Monday). For months without a 31st, `day: 31` falls back to the last day.

Evaluation must be done in the configured timezone, not UTC.

## Time and timezone

- The app has one configured timezone (`settings.timezone`).
- The server reads system time as UTC and converts to the configured TZ for any human-facing logic (rollover, recurrence, "today", quiet hours).
- Use `date-fns-tz` (or `Temporal` once stable in Node) for all TZ-aware math. Never use `new Date()` arithmetic for day-level logic.
- Day rollover is at local midnight. The scheduler uses a cron expression in the configured TZ.

## Frontend

- Routes:
  - `/` — wall dashboard (read + tick).
  - `/admin` — configuration UI.
- TanStack Query keys are stable and hierarchical, e.g. `["tasks"]`, `["tasks", taskId]`, `["instances", date]`. SSE handlers invalidate by prefix.
- Optimistic updates on tick-off. On error, revert and toast.
- Animations should never block input. Tick-off must register instantly even mid-animation.
- Audio uses Howler with a single shared instance pool. Respect quiet hours from `settings`.

### Component folder structure

Features live under `src/features/<name>/`. Each feature has a flat root for shared files (`types.ts`, `store.ts`, `utils.ts`, `hooks/`, `api/`) and a `components/` folder for UI.

Within `components/`, **top-level components** — those used directly by the page component — each get their own sub-folder:

```
components/
└── CalendarColumn/               # top-level component folder
    ├── CalendarColumn.tsx        # the component itself
    ├── index.ts                  # re-export only: export { default } from './CalendarColumn'
    └── components/               # private sub-components
        ├── WeatherSection.tsx
        ├── WeatherDay.tsx
        ├── CalendarSection.tsx
        └── AppointmentTile.tsx
```

Rules:
- `index.ts` files **re-export only** — no component code lives in them.
- Sub-components inside `ComponentName/components/` are private to that top-level component. Never import them from outside their parent folder.
- One component per file. Arrow function syntax only (`const Foo = () => ...`).
- Import depth: sub-components at `ComponentName/components/X.tsx` use `../../../` to reach the feature root (`types.ts`, `store.ts`, `utils.ts`, `hooks/`).
- Never import from deep paths inside another feature — only from a feature's root `index.ts`.

## Language

- All user-facing strings are in German — labels, button text, section headers, error messages, placeholder text, everything visible to the user.
- Code stays in English: variable names, comments, API field names, log messages, Zod schema keys.
- No i18n library — the app is German-only with no localization planned.
- Format dates in German: use `date-fns/locale/de` for day/month names, `dd. MMMM yyyy` pattern (e.g. "1. Mai 2026"). Weekday names in full: "Montag" through "Sonntag".

## Testing

- Vitest for unit tests in both `apps/web` and `apps/server`.
- Server: focus on recurrence evaluation, rollover logic, and API handlers (with an in-memory SQLite).
- Frontend: focus on store reducers and pure-logic helpers. UI snapshot tests are not required.
- Aim for tests on anything date/time/recurrence-related — these are the bug-prone areas.

## Logging

- Server: Pino with pretty-print in dev, JSON in production. Log level via `LOG_LEVEL` env var.
- Never log full OAuth tokens. Log token IDs or last-4 only.
- Never log uploaded photo contents.

## Photos and uploads

- Stored under `uploads/` (outside the repo, mounted at the same path as the DB).
- Served by the Hono server with long cache headers.
- On upload, resized to a max dimension (e.g. 512px) using `sharp`. Originals discarded.

## Secrets

- Google OAuth client ID/secret, encryption keys, etc. live in a `.env` file outside the repo.
- On the Pi, `.env` lives at `/etc/family-planner/.env` with `0600` permissions, owned by the service user.
- The repo contains `.env.example` with the variable names but no values.
